The "No Objects Allowed" ArchitectureAs we discovered, PyMC-BART slows down because it constantly spawns and modifies Python Node and Tree objects inside the step loop. To make our custom _patched_astep fly, we must translate the concept of a "decision tree" into flat, pre-allocated NumPy arrays.For a model with $M$ trees and a maximum of $K$ nodes per tree, we pre-allocate a rigid 3D matrix (or a set of parallel 2D arrays) at the very beginning of the .fit() call.We define the state of the entire ensemble using five primitive arrays of shape (M, K):F (Feature Index): Integer array. Which column of $X$ is this node splitting on? (Leaf nodes = -1).T (Threshold): Float array. The continuous value the feature is split against.L (Left Child): Integer array. The index of the left child node.R (Right Child): Integer array. The index of the right child node.V (Value): Float array. The predicted hazard contribution if this node is a leaf.The Survival Engine WorkflowInside our custom astep, we intercept PyMC's sampling loop. No PyTensor graph evaluations allowed.The Metropolis-Hastings Router: If the likelihood ratio is accepted, we keep the array updates. 1. The Sparsity Prior Update (Mathematical Flaw)The Issue: Look at your astep function: self.alpha_vec += var_counts.astype(np.float32). This is a linear accumulation of counts. Over thousands of iterations, your alpha_vec will grow to massive, infinite numbers.The Standard Method: This creates a "rich get richer" runaway effect where whatever features were lucky enough to be split on during the tune phase will permanently dominate the roulette wheel. Real Sparse BART (Linero, 2018) uses a Dirichlet-Multinomial conjugate update. The alpha_vec should be used to define a Dirichlet distribution, and you must periodically draw a new set of strict probabilities (summing to 1) from that distribution, rather than just endlessly stacking integers.2. The scipy.stats.truncnorm Performance BottleneckThe Issue: Your Numba C-engine is lightning fast, but you are drawing the latent $Z$ variable in pure Python using SciPy before passing it down.The Standard Method: SciPy’s truncnorm.rvs is notoriously slow when called sequentially inside an MCMC loop. For $10,000$ patients over $2,000$ iterations, that is $20$ million SciPy calls. This single Python block will easily eat 80-90% of your total computation time. A production package usually implements a fast rejection-sampler for the truncated normal directly inside the Numba loop to bypass the Python/C interface overhead.3. Unordered Categorical VariablesThe Issue: Your tree walk logic and your create_split_grid rely exclusively on the less-than-or-equal-to (<=) operator.The Standard Method: This mathematically forces an ordinal relationship onto every variable. If you pass an unordered categorical variable like "Race" (e.g., 1=White, 2=Black, 3=Asian), the tree is forced to split them sequentially (e.g., White and Black vs. Asian). Standard BART requires you to either handle nominal splits natively in the tree search (checking for exact equality sets) or mandate that the user explicitly one-hot encode all categorical variables before passing the $X$ matrix into the model.4. Standard BART packages often implement "Missing Incorporated in Attributes" (MIA). Instead of dropping patients with missing data, the algorithm is given the option to deterministically send all NaN values to the left child or the right child during a split, allowing the tree to learn if the absence of data is a predictor of survival.5.
